> **Status: in progress.** This page lists what the `nanyx` executable does today. It is part of the
> [compilation](./compilation) workstream. [Files and projects](../getting-started/files-and-projects) is the
> user's guide to running code.

`nanyx` is a small C# CLI over the compiler pipeline (`Nanyx.Compiler.Cli`), implemented with Consolo. Its
entrypoint and help text are generated by Consolo from the command method in `Program.cs`.

# Usage

```
nanyx run [--timings] [--check-memory] [--no-inline] <file.nyx> [<arguments>]
nanyx check <file.nyx> [--timings]
nanyx parse <file.nyx>
nanyx wasm <file.nyx> [--out <path>]
nanyx run [--timings] [--check-memory] [--no-inline] [--host <module>] [<directory or .nyxp> [<arguments>]]
nanyx check [<directory or .nyxp>] [--timings] [--host <module>]
nanyx build [<directory or .nyxp>] [--out <path>] [--timings] [--host <module>] [--no-inline]
nanyx new <name> [<directory>]
nanyx format [--check | --write] <files or directories>
nanyx format [--check] --stdin
nanyx stdlib-docs [--check] <directory>
nanyx search <query>
nanyx lsp
nanyx hello
```

- `run` compiles the file and executes it on the embedded Wasmtime engine. The program's output is the
  only thing written to stdout; diagnostics go to stderr. What follows the file or package is the program's own:
  `nanyx run tool.nyx a b` passes `a` and `b`, which the program reads with `args()` from
  [`nanyx/env`](../stdlib/env). The program sees the process's environment variables, through `variable`, and
  `exit(code)` ends it with that exit code, which `run` exits with. To pass arguments to the package in the
  current directory, name it: `nanyx run . a b`. An argument that starts with `-` can't be passed yet: the CLI reads it as one of `run`'s options, and `--` doesn't end them.
- `wasm` writes WebAssembly text next to the input (or to `--out`, making its directory if need be).
- `check` prints the compile phase and diagnostics, then the type of each top-level def the file declares, in
  source order, as hover writes it, with type variables `a`, `b`, ...: `greet : string -> string`, or
  `twice : [ToString(a)] a -> string` for a def that requires a context. It prints nothing from the prelude or
  the file's imports (`TypeHints.topLevelTypes`).
- `parse` prints the AST.
- `format` rewrites the files that are not formatted, or with `--check` lists them and exits with 1. With `--stdin`
  it formats standard input to standard output (see [Formatter](./formatter)).
- `stdlib-docs` writes the generated reference of each standard-library page in the directory it is given,
  `docs/src/content/stdlib`, from the library's doc comments, or with `--check` lists the pages that are out of date
  and exits with 1. It also fails for a file of the library that has no page, and a page that has no file (see
  [Standard library implementation](./standard-library-implementation#its-pages-on-the-docs-site)).
- `search` searches the standard library by name, by type, or both, and prints what matches, best first: each
  match's signature as hover writes it, the import it needs and the contexts it still needs at the types it was
  matched at. The query is a name (`nanyx search trim`), a type written as a def's annotation is
  (`nanyx search "bool -> string"`), or a name and a type with a colon between them
  (`nanyx search "trim: string -> string"`). A name finds the names that contain it; a type, the functions and
  values whose types can be made equal to it (see
  [Search by type](./info-view-and-library-browser#search-by-type) for the rules and the ranking). It exits with 1
  when nothing matches, and with 2 when the query is not a type.
- `lsp` runs the language server over standard input and output (see
  [Language server and editor](./language-server)).

`run`, `build` and `wasm` are debug builds: they compile a program with type or name errors all the same, and
report each error if the program reaches it. `build --release` and `wasm --release` refuse them (see
[Deferred errors](./deferred-errors)).

`run --check-memory` checks the program's reference counting as it runs (`WasmOptions.CheckMemory`; see
[Memory management](./memory-management)). It stops with exit code 70 at a block freed twice or an object counted
after it was freed. When the program finishes with blocks it never freed, it fails with 1. The Wasm tests run every
program this way, so a leak anywhere fails a test.

`run --no-inline` and `build --no-inline` compile every call as a call (`WasmOptions.Inline`; see
[Inlining](./inlining)). Inlining changes no behaviour, so this is for working on the compiler: a program that
misbehaves only when inlined points at the inliner. The tour examples are run both ways, and must print the same.

Every command exits with the same codes (`UsageError` in `Program.cs`; `ExitCodeTests.fs`):

- **0** when it succeeds. A program that `run` runs exits with its own status instead.
- **1** when the code has errors, a package's manifest can't be read or found, or the program fails.
- **2** when the command is used wrongly: more than one path (`run` takes the rest as the program's arguments), a file or manifest that does not exist, or an
  option's value it doesn't take. `format` also exits with 2 for a file it could not format.

`nanyx hello` takes no file: it compiles and runs a "hello world" program built into the CLI, as a
quick check that the compiler and runtime work.

# The stopwatch

While `run`, `build`, `check` or `wasm` compiles, a stopwatch on stderr names the file the compiler is on and how
long the compile has taken, rewritten in place ten times a second: `Compiling src/main.nyx… 4.7s`. While that
file's compile is checking a module it imports, the stopwatch names it too, as a chain: `Compiling src/main.nyx ›
nanyx/list… 1.2s` is the first file paying for the standard-library modules the whole build will share. When the
compile finishes it is replaced by `Compiled greeter (12 files) in 4.7s`, or `Compiled main.nyx in 1.2s` for a
script, and the diagnostics follow. It is shown only when stderr is a terminal: a pipe, a log file and CI see
nothing, and the command's other output is the same either way (`CompileProgress.cs`). Its line is cut to the
terminal's width, so it never wraps onto a line it can't rewrite. For `run`, it is drawn in
[the run's box](#the-runs-box) when there is one.

The compiler reports to the CLI through a `CompileListener` (`CompileListener.fs`): a package build says which file
it is on, and every compile says when each module's check starts and ends, by the module's full path or
`nanyx/<module>` for the standard library. `Package.buildReporting`, `Script.compileFileReporting` and the other
`…Reporting` functions take a listener; the functions without the suffix tell nobody. A standard-library module is
checked once per process, so only the first compile that needs it reports its check, and later ones report it reused.

## Timings

`run --timings`, `build --timings` and `check --timings` also record how long each module's check took, and write
them to stderr as a tree after the stopwatch's final line, whether or not stderr is a terminal (on a terminal, the tree
is also shown while the compile runs: see [the live view](#the-live-view)):

```
src/greetings.nyx (0.05s of 1.28s)
└── nanyx/prelude (1.23s)
src/main.nyx (0.20s of 1.06s)
├── nanyx/prelude (cached)
├── nanyx/console (0.04s)
│   └── nanyx/prelude (cached)
├── nanyx/list (0.81s)
│   └── nanyx/prelude (cached)
└── src/greetings.nyx (cached)
Emitted the program in 0.031s
```

Each line is a module's check, as `name (self of total)` in seconds. A module's imports are checked inside its own
check, so they are under it, in the order they were checked: the total is from the start of the check to its end,
imports included, and self is what is left once the imports' own totals are taken off, the module's own parsing,
desugaring and type checking (`CompileTimings`, `ModuleCheck.tree`). When the two are the same as written, to two
decimals, the line has one time, `name (0.04s)`, as most modules that import nothing unchecked do. A package build has a line at the left for each
source file, in the order it compiles them. A module is checked once per build, and a standard-library module once
per process, so where one is needed again it is `name (cached)`, with nothing under it: the compiler tells the
listener `ModuleReused` there. Emitting the program to WebAssembly happens per file after checking, not per module, so
it is one line of its own after the tree.

### The live view

When stderr is a terminal, `--timings` also replaces the stopwatch's line with the tree as it grows, redrawn in place
on the same tick:

```
src/catalogue.nyx (0.09s of 1.24s)
src/logging.nyx (0.1s…)
├── nanyx/prelude (cached)
└── nanyx/text (0.1s…)
    └── nanyx/prelude (cached)
```

A check under way shows how long it has taken so far, `(0.1s…)`, and takes its final form, `(self of total)` or `(total)`, when it
finishes. A finished check is one line, without what it needed, so the live view is the chain of checks under way,
each with its finished imports, and stays short however many modules there are. When it is taller than the terminal,
the lines nearest the check under way are kept and the rest are one line at the top, `… 12 more`. When the compile
ends, the live view is erased and the `Compiled …` line and the full tree are written as above.

The frame is built by `ModuleCheck.live` from `CompileTimings.SoFar`, the checks finished and under way at a moment,
and `CompileProgress` draws it with ANSI escapes (cursor up, clear line), cutting each line to the terminal's width so
none wraps. On Windows it turns on virtual terminal processing for the console first; where that can't be done, the
stopwatch stays the single line it is without `--timings`. A pipe or a log sees only the finished tree, as before.

## The run's box

`run` writes the compiler's output and the program's to the same terminal. When stderr is a terminal and the compiler
writes more than its stopwatch's line, what it writes goes in an open-sided box, and the program's output follows it
unmarked:

```
╭─ nanyx run emails ───────────────────
│ Compiled emails (3 files) in 1.9s
│ src/main.nyx:12:5: error NYX0102: Unknown function 'lookup'
│    |
│ 12 |     lookup(id)
│    |     ^^^^^^
│ Running with 1 deferred error
╰─ output ─────────────────────────────
invalid user id
23
```

The top rule is titled with the command, `nanyx run <package or file>`, and each line the compiler writes has a `│ `
gutter: the stopwatch, the timings tree and its live view, diagnostics, `Emitted …` and `Running with …`. There is no
right border, so a long line or a resized terminal can't break the box, and the rules span the terminal's width (or 80
columns when the console can't say). On a terminal in colour, the gutter, the rules and the compiler's own lines are
dimmed; diagnostics keep their colours, and their underlines stay aligned, since every line moves two columns right.
Where the console's code page has no rounded corners, as code page 437 on Windows hasn't, the corners are `┌` and `└`.
When the program doesn't run, because of an error that can't be deferred, the box ends with a plain rule. What the run
reports after the program, such as `Runtime error: …`, follows the program's output, unmarked.

A plain run, with nothing to say but `Compiled … in`, gets no box. The compiler doesn't know that until the compile has
finished, so the stopwatch leaves its final line open, without its line ending: if the compiler writes nothing more,
the line is ended before the program runs, and if it writes a line, the top rule is written over the stopwatch's and
the stopwatch's line moves into the box. With `--timings`, the tree always follows, so the top rule is written when
the compile starts and the live view is drawn inside the box. A pipe or a log sees no box, and the same bytes as
before (`RunBox.cs`, `RunBoxTests.fs`).

# Packages

Given a directory or a `.nyxp` manifest instead of a file, or nothing at all, `run`, `build` and `check`
work on a package: the manifest in that directory (the current one by default) or the nearest directory
above it.

- `build` checks every source file the manifest's `sources` select, with the linters its `linters`
  turns on, and writes the program of the package's `@entry` to `out/<package name>.wat` beside the
  manifest (or to `--out`). A package without an `@entry` is only checked.
- `run` does the same checks, then runs the `@entry`.
- `check` does the same checks and writes nothing. Any error fails it, including one a debug build would defer.

The package's `@entry` runs under the host its manifest's `host` names,
`(package = "nanyx.console", version = "0.28.0")`, or `nanyx/console.host` without one (see
[Hosts](./hosts#choosing-a-host)). `--host <module>` chooses another for one command, in place of the manifest's. A
`--host` that isn't one of the standard library's, or a module that isn't a host, is an error that names it, and so
is a manifest's `host` package other than `nanyx.console`, or `settings` for it; `--host` on a single `.nyx` file is a
usage error, since a script always runs under the console host.

`nanyx new acme.demo` makes a package in a new directory, `demo` (the name's last segment) unless another
is given: `acme.demo.nyxp`, with the official linter on and the console host, both at the compiler's version, and
`src/main.nyx`, whose `@entry` prints "Hello, World!". The name must be one the manifest accepts, and the directory
must be new or empty.

A package runs only the linters its manifest names (an entry with `package = "nanyx.lint"` for the official one), and
a file run on its own only those its `::linters` directives name (`::linters.default`, or
`::linters.default.unusedBindings = "error"` to set a rule's severity too). Without either, no linter runs. See
`examples/greeter` for a working package, and `examples/directives.nyx` for a script with directives.
